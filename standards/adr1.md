# ADR-1: Використання нативного Node.js та драйвера MongoDB без сторонніх фреймворків

## 2. Контекст і постановка проблеми

При розробці вебзастосунку для інтернет-магазину автозапчастин постало питання вибору технологічного стека для серверної частини та взаємодії з базою даних. Розробник має попередній досвід роботи з нативним Node.js, MongoDB та чистим JavaScript (Vanilla JS/HTML/CSS), проте не має практичного досвіду роботи зі сторонніми бекенд-фреймворками (такими як Express, NestJS) чи ODM-бібліотеками (наприклад, Mongoose).

Потрібно визначити, чи варто витрачати час на вивчення нових фреймворків, чи зосередитися на реалізації функціоналу за допомогою знайомих інструментів, щоб уникнути зайвого стресу та затримок у розробці.

## 3. Альтернативи

### Альтернатива 1: Нативний Node.js (`http` модуль) + Офіційний нативний MongoDB Driver (Обрано)

- **Плюси:**
  - Повна відсутність порогу входження та потреби вивчати нові сторонні бібліотеки.
  - Повний контроль над кодом та розуміння кожного процесу «під капотом» (як обробляються запити, потоки, підключення).
  - Менше зайвих залежностей (dependencies).
- **Мінуси:**
  - Потребує самостійного написання базової маршрутизації (routing) та парсингу тіла HTTP-запитів, які у фреймворках зазвичай вирішуються «з коробки».

### Альтернатива 2: Node.js + Express.js + Mongoose ODM

- **Плюси:**
  - Стандартний промисловий підхід, лаконічний код для роутів, готові інструменти валідації схем через Mongoose.
- **Мінуси:**
  - Необхідність витрачати час на вивчення нової документації, архітектури middleware та концепцій Mongoose з нуля, що підвищує ризик помилок через незнання інструменту.

### Альтернатива 3: Використання комплексного фреймворку (наприклад, NestJS)

- **Плюси:**
  - Жорстка корпоративна архітектура, вбудована модульність та підтримка TypeScript.
- **Мінуси:**
  - Надмірна складність (overengineering) для поточного проєкту, дуже високий поріг входження для розробника, який не має досвіду з нативним Node.js рівня вище базового.

## 4. Рішення

Використовувати **нативний модуль `http` у Node.js** для створення серверної частини та **офіційний нативний драйвер `mongodb`** для роботи з базою даних. На фронтенді використовувати **Vanilla JS, HTML та CSS** без важких фреймворків. Маршрутизацію та обробку запитів організувати через власні модульні файли роутів та контролерів на базі нативних можливостей Node.js.

## 5. Пояснення (Чому обране рішення найкраще)

Цей варіант є оптимальним, оскільки спирається на наявний досвід розробника. Він дозволяє сфокусуватися на логіці інтернет-магазину (каталог, кошик, замовлення, оформлення) та архітектурі застосунку загалом, а не на подоланні «кривої навчання» незнайомих фреймворків. Це забезпечує максимальну прозорість коду та впевненість у кожній написаній системній інструкції.

## 6. Наслідки

- **Позитивні:**
  - Швидкий старт реалізації бізнес-логіки.
  - Відсутність проблем із несумісністю версій сторонніх важких бібліотек.
  - Глибоке розуміння того, як працюють HTTP-сервери та бази даних на базовому рівні.
- **Негативні:**
  - Деякі стандартні речі (наприклад, складний роутинг чи парсинг JSON-даних із POST-запитів) доведеться писати самостійно з використанням вбудованих засобів Node.js.
- **Нейтральні:**
  - Архітектура бекенду буде побудована на власних принципах організації папок і файлів (routes/controllers), а не на загальноприйнятих конвенціях фреймворків на кшталт Express.

# ADR-7: Інтеграційні й E2E-тести — локальні процеси mongod (mongodb-memory-server) із підтримкою зовнішніх URI, а не моки драйвера

## Status

Accepted

## Context

`orderRepository` має два шляхи (`withTransaction` на replica set і компенсація на standalone, `adr/adr5.md`). У `adr5` прямо сказано, що `withTransaction` «не перевірено в автоматичних тестах без replica set», а код mongo-репозиторіїв раніше виконувався лише проти імітації драйвера. Завдання 3 вимагає інтеграційні тести з піднятою справжньою залежністю й одну команду запуску.

## Decision Drivers

- Критичний ризик живе в поведінці БД (умовний `$inc`, унікальні індекси, транзакції, гонки), яку мок драйвера не відтворює (РПЗнП 7.7).
- Обидва шляхи `adr5` (`standalone` і `replica set`) мають виконуватися реально.
- Одна команда запуску на чистій машині; випадкові порти та ізоляція баз без доступу до чужих БД (РПЗнП 7.11).
- Мінімум коду, що існує лише для тестів (РПЗнП 7.5.1).
- Обмеження робочого середовища: на системному диску `C:` критично мало вільного місця (`0 ГБ`), через що розгортання WSL 2 та Docker Desktop неможливе; потрібен запуск справжнього бінарника `mongod` із можливістю зберігати кеш на диску `D:`.

## Considered Options

### Варіант 1: Моки/фейки драйвера `mongodb`

- **Плюси:** швидко, не потребує запуску процесів БД.
- **Мінуси:** мок усе одно треба перевіряти на справжній БД; великий обсяг коду лише для тестів; саме так `withTransaction` лишився неперевіреним.

### Варіант 2: `docker compose` із двома MongoDB — standalone і одновузловий replica set

- **Плюси:** повна відповідність контейнерному продакшн-оточенню; випадкові порти, `tmpfs`, очищення через `down -v`.
- **Мінуси:** вимагає встановленого Docker Desktop і WSL 2 із кількома гігабайтами вільного місця на диску `C:`, чого немає на робочій машині. Залишено як підтримуваний зовнішній режим для CI.

### Варіант 3: `mongodb-memory-server` (локальні процеси `mongod` у режимах standalone та replica set) (обрано)

- **Плюси:** піднімає справжній бінарний сервер `mongod` (а не мок драйвера), підтримує `MongoMemoryReplSet` із реальними транзакціями (`wiredTiger`), не потребує Docker/WSL 2 і дозволяє перенести кеш бінарників на диск `D:` через змінну середовища `MONGOMS_DOWNLOAD_DIR`.
- **Мінуси:** під час першого запуску завантажує бінарник MongoDB (~70–100 МБ, потрібна мережа); підняття `replica set` додає кілька секунд до кожного запуску `npm test`.

## Decision

Варіант 3. Оркестрація — `scripts/test-all.js` (`npm test`) автоматично піднімає `MongoMemoryServer` (standalone) та `MongoMemoryReplSet` (одновузловий replica set із рушієм `wiredTiger`) на випадкових портах і гарантовано зупиняє процеси у `finally`. Якщо в середовищі (наприклад, у CI з готовими Docker service-контейнерами) уже задані змінні `TEST_MONGO_URI` і `TEST_MONGO_RS_URI`, раннер підключається до них без запуску локальних процесів. Ізоляція даних: окрема база на тестовий файл (`ap_it_<pid>_<ts>`), кожен тест працює зі своїми даними.

## Consequences

- **Позитивні:** закрито розрив «withTransaction не перевірено» без залежності від Docker на робочій машині; тест на збій запису після списання ловить видалення компенсації; збережено сумісність із Docker-сервісами в CI через змінні середовища.
- **Негативні:** перший прогін потребує завантаження бінарника `mongod`, а старт `replica set` сповільнює `npm test` → хук `pre-push` запускає легкий `npm run test:fast`, а повний `npm test` виконується перед PR та в CI.
- **Нейтральні:** `memory`-прогін лишається швидким герметичним шаром і базою для мутаційного тестування Stryker.

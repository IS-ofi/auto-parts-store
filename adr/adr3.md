# ADR-3: Модульна структура моноліту (Клієнт-Сервер)

## 2. Контекст і постановка проблеми

При проєктуванні архітектури інтернет-магазину автозапчастин на нативному стеку (Vanilla JS, нативний Node.js без фреймворків) постало питання організації вихідного коду. Якщо розмістити всю логіку в одному чи кількох глобальних файлах, код швидко стане монолітним, складним для підтримування, тестування та розширення. Потрібно було визначити чітку структуру директорій та модульний поділ для клієнтської частини, бекенду й контролерів, яка б забезпечила ізоляцію бізнес-логіки та відповідність технічній специфікації (`spec.md`).

## 3. Альтернативи

### Альтернатива 1: Модульна структура з розділенням на клієнт (`client/`), серверні роути (`server/routes/`) та контролери (`server/controllers/`) (Обрано)

- **Плюси:**
  - Чіткий поділ зони відповідальності: клієнтські сторінки та скрипти ізольовані від серверної бізнес-логіки.
  - Окремі файли роутів (`authRoutes.js`, `productRoutes.js`, `orderRoutes.js`) та контролерів полегшують масштабування API та аудит коду.
  - Повна прозорість взаємодії через нативний модуль `http` та Fetch API.
- **Мінуси:**
  - Потребує створення більшої кількості файлів та директорій на старті проєкту порівняно з єдиним файлом сервера.

### Альтернатива 2: Усе в одному файлі (`server.js` та єдиний `index.html`)

- **Плюси:**
  - Максимальна простота на найперших етапах написання коду без необхідності управляти багатьма імпортами.
- **Мінуси:**
  - Повне порушення принципів модульності та чистої архітектури. Неможливість нормально підтримувати окремі сторінки (авторизація, кошик, wishlist, адмінка) та розділяти роботу роутів і контролерів.

### Альтернатива 3: Класична багаторівнева архітектура з глибокою ієрархією сервісів та репозиторіїв (як у Enterprise NestJS)

- **Плюси:**
  - Максимальна декомпозиція для дуже великих ентерпрайз-систем.
- **Мінуси:**
  - Надмірна складність (overengineering) для навчального проєкту на нативному Node.js без фреймворків, що призведе до зайвого ускладнення коду (boilerplate).

## 4. Рішення

Затвердити двокомпонентну монолітну структуру проєкту з виділенням окремих папок `client/` (із розбиттям на сторінки `auth.html`, `product.html`, `wishlist.html`, `cart.html`, `checkout.html`, `admin.html` та скрипти) і `server/` (із розподілом на точку входу `server.js`, підключення до БД `db.js`, контролери бізнес-логіки в `server/controllers/` та модульні роути в `server/routes/`).

## 5. Пояснення (Чому обране рішення найкраще)

Ця структура є найкращою, оскільки вона дозволяє реалізувати повноцінний маркетплейс автозапчастин із розширеним функціоналом (каталог, поліморфні атрибути товарів, кошик, список бажаного, замовлення з доставкою й оплатою та адмін-панель) на нативному стеку без хаосу в коді. Кожен компонент і роут має своє чітко визначене місце, що робить кодову базу читабельною та легко перевірюваною під час аудиту.

## 6. Наслідки

- **Позитивні:**
  - Логіка кожного модуля (авторизація, товари, замовлення) чітко ізольована.
  - Легкість пошуку помилок та додавання нових ендпоінтів у відповідні файли роутів чи контролерів.
- **Негативні:**
  - Вимагає суворого дотримання прийнятої структури під час додавання нових файлів.
- **Нейтральні:**
  - Архітектура базується на власній структурі папок нативного Node.js, а не на автогенерованих каркасах фреймворків.

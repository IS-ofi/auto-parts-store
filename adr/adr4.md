# ADR-4: Керування залежностями та передавання бізнес-контексту (Business-Process ID) за допомогою AsyncLocalStorage

## 2. Контекст і постановка проблеми

Згідно з архітектурними вимогами завдання, заборонено «протягувати» 10–15 параметрів (dependency hell) через сигнатури кожної функції (роути -> сервіси -> репозиторії). Водночас ініціалізовані ресурси (наприклад, підключення до БД) та унікальний ідентифікатор поточного бізнес-процесу (`business-process ID`) повинні автоматично потрапляти в кожен лог із будь-якого рівня програми.

Необхідно обрати підхід до керування залежностями та передавання контексту в середовищі нативного Node.js без використання сторонніх фреймворків інверсії контролю (DI-контейнерів на зразок InversifyJS).

## 3. Альтернативи

### Альтернатива 1: Ручне прокидування параметрів (Parameter Drilling)

- **Плюси:**
  - Максимальна простота реалізації без використання додаткових API.
- **Мінуси:**
  - Порушення чистоти коду, роздування сигнатур функцій зайвими аргументами (`req, res, db, processId, userId`), високий ризик людської помилки при пропуску параметрів.

### Альтернатива 2: Глобальний реєстр стану / Singleton (глобальна змінна)

- **Плюси:**
  - Швидкий доступ до ресурсів із будь-якого файлу програми.
- **Мінуси:**
  - Проблеми з конкурентністю (race conditions) при паралельних HTTP-запитах в асинхронному середовищі Node.js — контекст одного користувача може перезаписати контекст іншого.

### Альтернатива 3: Використання вбудованого модуля `AsyncLocalStorage` (Обрано)

- **Плюси:**
  - Надійне збереження ізольованого контексту для кожного окремого асинхронного ланцюжка запитів (request-scoped context).
  - Відсутність потреби тягнути параметри через аргументи функцій — доступ до контексту можливий із будь-якого рівня програми в будь-який момент часу.
  - Відсутність сторонніх залежностей (входить до стандартної бібліотеки Node.js).
- **Мінуси:**
  - Вимагає розуміння асинхронної моделі виконання JavaScript (Async/Await та асинхронних ресурсів).

## 4. Рішення

Використовувати вбудований у Node.js модуль **`AsyncLocalStorage`** для управління залежностями та автоматичного прокидування `business-process ID` і системного контексту. На старті обробки HTTP-запиту в `server.js` ініціалізується унікальний контекст запиту, який автоматично супроводжує всі подальші виклики шарів бізнес-логіки та репозиторіїв без необхідності передавати його явно через параметри функцій.

## 5. Пояснення (Чому обране рішення найкраще)

Це рішення ідеально відповідає наскрізній вимозі не протягувати параметри через усю систему, забезпечуючи водночас потокобезпечність (thread-safety в асинхронному контексті) для паралельних запитів. Оскільки `AsyncLocalStorage` є частиною core-модулів Node.js, це не додає зайвого роздування коду і повністю відповідає концепції «без важких фреймворків».

## 6. Наслідки

- **Позитивні:**
  - Чисті сигнатури функцій у контролерах і репозиторіях.
  - Гарантоване автоматичне потрапляння `business-process ID` у кожен лог чи помилку незалежно від глибини виклику.
  - Повна ізоляція даних між різними паралельними запитами клієнтів.
- **Негативні:**
  - Дещо ускладнюється дебагінг через неявне передавання контексту «під капотом».
- **Нейтральні:**
  - Вимагає суворого дотримання стандарту ініціалізації контексту на вході в HTTP-сервер.

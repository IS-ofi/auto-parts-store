Spec — Завдання 3: тестування і верифікація AutoParts Hub

Мета: перевірити критичну логіку оформлення замовлень, списання залишків та ідемпотентність на всіх рівнях (unit, інтеграційні з реальною MongoDB та E2E), а також переконатися за допомогою мутаційного тестування, що самі тести реально ловлять помилки.

## Рівні тестування:

Unit-тести: герметична перевірка чистих функцій валідації, обробки помилок, парсингу позицій та підрахунку суми замовлення без мережі й бази даних — усі гілки та граничні значення.

Інтеграційні тести: перевірка оформлення замовлення (orders.place) і спільних API-сценаріїв на справжній MongoDB у Docker у двох режимах — standalone та replica set.

E2E-тести: HTTP-запити до окремо запущеного процесу сервера з прямою перевіркою колекцій у базі даних та перевіркою аварійного завершення при недоступній БД.

## Критерії прийняття:

Одна команда запуску: npm test автоматично піднімає дві ізольовані інстанції справжнього сервера MongoDB (standalone та replica set на випадкових портах через mongodb-memory-server або підключається до зовнішніх TEST_MONGO_URI / TEST_MONGO_RS_URI у CI), проганяє всі рівні тестів і завершує процеси БД з кодом 0.

Ізоляція та повторний прогін: npm test -- --runs 2 проходить двічі поспіль без витоку даних між запусками (окрема тимчасова БД під кожен тестовий файл з очищенням після виконання). Швидкі тести npm run test:fast працюють без Docker і запускаються на pre-push.

Покриття гілок: модулі validation.js та errors.js покриті на 100% за рядками й гілками, включно з граничними значеннями (рядки 200/201 символів, ObjectId 23/24/25 hex, кількість 0/1, NaN, Infinity, числа у вигляді рядків).

Ключові інваріанти замовлення виконуються на всіх джерелах даних (memory, standalone, replica set):

- можна замовити весь залишок товару до останньої одиниці, а спроба замовити на 1 більше повертає помилку 409;

- однаковий Idempotency-Key від різних користувачів (userId) створює два незалежні замовлення;

- підрахунок суми замовлення не має похибки чисел із плаваючою точкою (0.1 × 3 === 0.3).

Стійкість у MongoDB: збій запису замовлення після списання товару повертає залишки назад (компенсація у standalone, відкат транзакції у replica set); 10 одночасних замовлень на залишок у 5 шт. дають рівно 5 успішних; 5 паралельних повторів одного ключа ідемпотентності створюють 1 замовлення.

E2E-поведінка: після HTTP-запиту на створення замовлення залишок, кошик і замовлення перевіряються напряму в колекціях MongoDB; запуск сервера без доступної БД завершується з кодом 1.

Мутаційне тестування: npm run mutation запускає Stryker поверх швидкого набору тестів для критичних модулів (валідація, помилки, HTTP-утиліти, сервіс замовлень, in-memory репозиторій). Усі вижилі мутанти класифіковані у reports/mutation-report.md (реальна прогалина, еквівалентний або прийнятний), а для реальних прогалин дописані тести.

Жодного продакшн-коду, написаного виключно для тестів.

## Що свідомо не робимо (out of scope):

Повне unit-покриття всього проєкту та контролерів — фокус лише на критичному модулі й реальній інтеграції.

Мутаційне тестування для MongoDB-репозиторіїв — запуск Stryker поверх Docker-тестів тривав би години, тому цей шар захищений інтеграційними тестами.

Окремий Makefile — для Node.js достатньо стандартних скриптів у package.json.

Браузерні E2E (Playwright), навантажувальні тести та перевірка JWT/ролей — відсутні в поточній ітерації продукту.

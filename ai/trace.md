# Слід роботи зі штучним інтелектом

Цей документ послідовно та детально фіксує всі промти, зауваження та відповідні зміни в специфікації та інфраструктурі по кожному з етапів розробки інтернет-магазину автозапчастин **AutoParts Hub**.

---

## 1. Етап 1: Ідея, репозиторій та README.md

### Промпт користувача:

> «Потрібно описати в README.md ідею застосунку інтернет-магазину автомобільних запчастин, його мету, ціль, можливості застосунку, вибір стеку технологій html, css, js, node, mongodb.»

### Зауваження та аналіз:

- Початковий варіант відповіді від ШІ помилково пропонував використання сторонніх інструментів (`Express.js` та `Mongoose`), які не входять до нашого нативного стека.

### Зміни:

- У файлі `README.md` зафіксовано концепцію AutoParts Hub, цільову аудиторію, функціональні можливості для клієнтів (каталог, пошук, підбір за авто, кошик, особистий кабінет) та адміністраторів (CRUD товарів, обробка замовлень), а також затверджено стек технологій: HTML5, CSS3, Vanilla JS, нативний Node.js та нативний драйвер MongoDB.

## 2. Етап 2: Налаштування пакетів, стилю коду та лінтера

### Промпт користувача:

> «Налаштуй у проєкті пакети, стиль коду, форматтер та лінтер/статичний аналіз для Vanilla JS та Node.js. Також налаштуй git-хуки (Husky) на commit (формат, лінтер) та push (мінімальний smoke-тест і збірка). Надай покрокові інструкції та конфігураційні файли (package.json, .prettierrc, .eslintrc тощо).»

### Зауваження та аналіз:

- Під час написання конфігурації `eslint.config.js` виникла синтаксична помилка TypeScript (`Declaration or statement expected`) через те, що експорт масиву було записано як `export [...]` замість стандартного дефолтного експорту.
- Для проходження суворих перевірок AI-CHECK знадобилося встановити пакет `@eslint/js` та додати правило `--max-warnings 0` у скрипт лінтера.

### Зміни:

- Виправлено синтаксис конфігурації лінтера на `export default [...]` у файлі `eslint.config.js`.
- Створено конфігурації `.prettierrc`, оновлено `package.json` та налаштовано Git-хуки Husky (`pre-commit` для лінту й форматування через `lint-staged`, а також `pre-push` для збірки та smoke-тестів).

## 4. Етап 4: Створення та ітеративне оновлення spec.md

### Промпт користувача 1:

> «Мені потрібно створити файл для застосунку інтернет-магазину автозапчастин spec.md, де вказане розбиття на компоненти/модулі та взаємодія; дані та зв'язки (напр. ER); як дані оновлюються за ключовими сценаріями. Стек технологій: html, css, js, node, mongodb.»

### Зауваження користувача до первинного виходу ШІ:

> «Повністю прибери згадки про Express.js та Mongoose, ми їх не використовуватимемо. Структура даних та зв'язки — зроби його у вигляді візуальної ER-діаграми, використовуючи синтаксис Mermaid.»

### Промпт користувача 2:

> «Оновіть spec.md. Додайте повну модульну структуру з урахуванням сторінок авторизації, обраного та карток товарів (auth.html, wishlist.html, product.html). ER-діаграму (Mermaid) зробіть для MongoDB з урахуванням поліморфних характеристик товару (attributes), кошика (CART), списку бажань (WISHLIST) та замовлень із доставкою/оплатою. Додайте ключові сценарії для авторизації, перегляду картки товару, замовлення та адмін-CRUD.»

### Промпт користувача 3 (фінальне уточнення роутів і структури):

> «Згенеруй технічну специфікацію spec.md для інтернет-магазину автозапчастин на Vanilla JS, нативному Node.js та MongoDB. У бекенді використай окремі файли роутів: authRoutes.js, productRoutes.js та orderRoutes.js. У ER-діаграмі (Mermaid) для баз даних зроби так, щоб колекції CART і WISHLIST містили однакові атрибути: ID (_id), ID користувача (user_id) та масив товарів (items або products).»

### Зміни в spec.md, що випливли з усіх зауважень та промптів:

1. **Повна відмова від сторонніх фреймворків та ODM:** Повністю вилучено будь-які згадки про Express.js та Mongoose. Закріплено використання виключно нативного модуля `http` у Node.js та офіційного драйвера `mongodb`.
2. **Розширена модульна структура:** Додано сторінки та клієнтські скрипти для авторизації (`auth.html`, `auth.js`), списку бажаного (`wishlist.html`, `wishlist.js`), детальної картки товару (`product.html`, `productDetail.js`), а також окремі серверні файли роутів (`authRoutes.js`, `productRoutes.js`, `orderRoutes.js`).
3. **Уніфікована ER-діаграма Mermaid:** Побудовано схему бази даних, де колекції `CARTS` та `WISHLISTS` мають ідентичну базову структуру (`_id`, `user_id`, `items`), товари містять поліморфний масив `attributes` для гнучких характеристик запчастин, а замовлення — вкладені об'єкти доставки й оплати.
4. **Ключові сценарії та критерії прийняття:** Детально описано життєцикл даних для сценаріїв авторизації, перегляду картки товару, оформлення замовлення та адмін-CRUD, а також додано розділ перевірних критеріїв прийняття (Acceptance Criteria).

## 5. Опрацювання зауважень AI-CHECK та фінальний план виправлень

Відгук викладача / AI-CHECK (Не пройдено):
«Конвеєр перевірок не працює: eslint.config.js використовує ESM import у пакеті з "type": "commonjs", а імпортований @eslint/js не встановлено... npm test у pre-push запускає 0 тестів; smoke-тесту й збірки в хуках немає. Обов'язкового аудиту немає: секції топ-3 і перевірки в DEFENSE закреслено, DEFENSE.md і adr/ у репозиторії немає. У spec.md немає перевірних критеріїв прийняття...»

### Зміни

1. Внесені зміни для усунення зауважень:
   Виправлення Lint-конвеєра: Встановлено пакет @eslint/js у devDependencies та додано прапорець --max-warnings 0 у скрипт lint для забезпечення нульової толерантності до попереджень.

2. Налаштування конвеєра хуків (Husky): Розподілено перевірки у git-хуках: на етапі pre-commit активовано лінтинг і форматування через lint-staged, а на етапі pre-push налаштовано виконання smoke-тестів і збірки.

3. Інтеграція критеріїв прийняття: Додано чіткі перевірні критерії прийняття (Acceptance Criteria) безпосередньо до файлу spec.md та до відповідного шаблону standards/spec-template.md.

4. Реорганізація структури ADR та папок: Створено повноцінну директорію adr/, куди перенесено й декомпозовано архітектурні рішення (зокрема файли adr1.md, adr2.md, adr3.md).

5. Проведення аудиту та заповнення DEFENSE.md: Здійснено реальний аудит розбіжностей із виділенням топ-3 пунктів, заповнено файл DEFENSE.md без закреслень із прив'язкою до комітів та дійсним посиланням на закритий GitHub PR

6. Фіксація сліду ШІ: Оформлено та збережено вичерпний документ із хронологією промптів, зауважень та ітеративних змін у каталозі ai/trace.md.
